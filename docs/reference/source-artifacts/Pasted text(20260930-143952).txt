Supplier Quotation and Customer Quotation are deliberately separate DocTypes (different commercial directions).

Supplier Request architecture
FJK Supplier Quotation Request (Deal link; template link; status Draft/Generated/Sent; generated file; send log). Only relevant sections rendered (template conditional). Sending uses native email; sending ≠ quotation received.

Template Builder architecture

Native Print Format Builder defines the request layout (sections/order/headings/tables/text/css).

Custom FJK Supplier Request Template provides versioning (template name/version; stores the Print Format reference + config snapshot) — native Print Formats are mutable, so versioning is the justified custom part.

A generated request retains template + template version + generated output + Deal + supplier + timestamp + send status + sent communication ref. Later template changes never alter historical generated requests (store the generated artifact).

Supplier email architecture (native)

Native: Email Account (outgoing + incoming IMAP), Communication, Email Template; frappe.sendmail(..., reference_doctype="FJK Supplier Quotation Request", reference_name=...).

Outgoing send is native-sufficient. Message-ID issued by Frappe; Communication stores message_id/in_reply_to (Communication fields verified).

Incoming reply architecture

Native inbound exists: Email Account.enable_incoming + IMAP; receive.py parses Message-ID/In-Reply-To, saves attachments, creates a Communication with reference_doctype/reference_name, and resolves the reference via thread (in_reply_to→Communication) or append_to/subject match.

Gap/risk: matching to a custom Request DocType depends on correct thread headers and Email Account append_to; failure modes: unmatched replies, duplicates, spoofed headers, mailbox permissions, supplier not replying in-thread (won't thread). If native proves insufficient → IMAP poller integration (future), not now.

Captured reply → pending supplier-response event (Communication linked to Request/Deal) → extraction/review.

Evidence preservation architecture

Original email (sender/recipients/subject/date/body/thread) → native Communication (source evidence).

Original attachment → native File (exact bytes, filename, MIME, timestamp), linked to Request/Deal and marked source evidence (minor link fields).

Structured extraction → custom fields/child on FJK Supplier Quotation Version (extraction status; reviewer; corrections; confirmed_at/by).

Original remains immutable; extracted data is a derived, non-authoritative layer.

Extraction / OCR architecture (PLAN only)

Deterministic: Excel (openpyxl), DOCX (python-docx), PDF text (pdfplumber/pypdf) — not installed; OCR (tesseract) — not installed; LLM — none.

Conceptual: Upload/Receive → identify type → extract → normalise → operator review → correct → confirm → store. Never auto-trust.

External service/model would be a future integration; not selected/installed now.

Supplier quotation versioning model

Parent FJK Supplier Quotation: supplier, Deal, request link, current_version, status.

FJK Supplier Quotation Version (submittable/immutable): received_date, validity_from/to, currency, totals, items (child), conditions/free-text (Long Text), requested_changes, source_document (File), supplier_response, requote_of (Link), previous_version.

Negotiation entries: child (date/actor/event/response).

Immutability via submit; previous versions cannot be overwritten (new version per change); mirrors the existing FJK Quotation Version pattern.

Validity / reconfirmation model

Represented as validity_from/validity_to on each version; computed is_expired/validity_state (derived, optionally cached).

On expiry: no "Deal Expired"; Deal stays open; mark version reconfirmation_required; create a new version (requote_of=old) on reconfirmation; original preserved with its original validity.

Operator informed via the workspace/summary (no notifications built now).

Info Complete state model

State on CRM Deal (fjk_info_complete bool/enum) + audit (who/when) via Comments/Version or small log.

Gating: quotation/request creation APIs check state; reopen → gate again.

Reopening does not delete quotation history nor auto-invalidate supplier quotations.

Permissions: Sales User may set; Sales Manager overrides; System Manager full.
